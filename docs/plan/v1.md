# Path to Tensor 1.0

[Documentation](../README.md) · [Milestone history](roadmap.md) · [Release preparation](../releases.md)

Planning baseline: **2026-10-05**. Status: proposed development plan. The package
is still `0.1.0`; milestones below describe work and acceptance criteria, not
features already shipped or promised release dates.

The [1.0 benchmark and demonstration program](v1-benchmarks.md) records the
requested Qwen comparisons against vLLM, SGLang and llama.cpp (with explicit
format qualification), FA/MLA/GDN forward/backward studies across
five GPUs, and sustained nanoGPT, image, audio, and full llama.cpp quantization
demonstrations. Its BENCH-01–09
items add concrete workload development and release evidence alongside M1–M5.

The [unified Tensor LLM engine plan](unified-llm-engine.md) extends the existing
optional `tensor-llm` package for both batch-1 latency and batched throughput.
Shared model resources, request state and execution infrastructure serve local
generation and continuous batching, with specialized kernel schedules. Its
LLM-01–07 stages implement the engine side of BENCH-03/04/09; an LFM2 pilot can
start alongside the relevant contract and M3 discovery work without waiting for
the complete release roadmap.

The proposed [tuning workbench and kernel recipes](tuning-workbench.md) adds a
shared human/agent profiling interface, bounded refinement loops, and verified
reconstruction from stored schedules. Minimal reports and recipes complement M3;
visual tooling and an agent controller are separately tracked enhancements.

## What 1.0 should mean

Tensor 1.0 should be a dependable toolchain for kernel authors: bring a TileLang
kernel, build and inspect it, explore explicit schedules, distribute a verified
artifact or module, and execute it through a small runtime.

The defining commitment is that a user can depend on the documented public
contracts across compatible releases. A completed experiment proves that a path
can work; a stable release also needs repeatable packaging, compatibility tests,
clear failure behavior, and a maintained support matrix.

This preserves the kernel-author scope in
[ADR 0006](../adr/0006-prototyping-surface-not-tensor-library.md). Standalone
autograd, general tensor algebra, arbitrary fusion, general GGUF coverage, and
universal backend/performance parity are separate development tracks.

## Proposed stability boundary

| Surface | Proposed 1.0 commitment | Boundary |
|---|---|---|
| Public Python workbench | Documented build, device/buffer, executable, event, validation, timing, interoperability, and manual-backward contracts | Freeze an explicit symbol/method inventory; internal implementation modules remain private |
| CLI | Documented commands, arguments, exit behavior, and machine-readable report schemas | Human-readable formatting can evolve; JSON fields need versioning |
| Executable artifacts and runtime ABI | Compatible previously released artifacts keep loading and executing on supported hardware | Package, artifact-format, ABI, and frontend versions remain independent |
| Modules | Named exports, content verification, exact dependency resolution, frozen/offline restoration, and explicit compilation | No implicit recompilation or unverified dependency substitution |
| Schedule discovery | Documented search/profile APIs and a small reusable producer trial workflow | Caller supplies the space, factory, reference, and metric; no automatic arbitrary IR optimization |
| CUDA / WebGPU | Correctness, resource/lifetime behavior, and clear capability failures for published support tiers | Exact CUDA SM and WebGPU feature/limit requirements continue to apply |
| Optional Torch / NN / LLM packages | Each publishes its own maturity and tested core compatibility | Core 1.0 does not automatically make these packages stable or expand their workload coverage |

The producer can remain pinned to one supported TileLang/TVM FFI stack at 1.0.
Compiler upgrades should be tested releases; serialized frontend IR is not a
cross-version compatibility promise. Consumers of executable images remain
independent of those compiler packages.

## What is already present

The [historical phases](roadmap.md) establish CUDA execution, independent runtime
descriptors, modules and transport wheels, PyTorch inference integration, native
WebGPU, and bounded manual training. Subsequent LFM2 workloads exercise larger
inference paths and schedule discovery.

The pre-1.0 preparation adds installation, migration and discovery guides, MIT
licensing, distribution metadata, source-archive checks, and an isolated consumer
check. These are implemented foundations. They still need release-specific CI,
hardware, compatibility, and external-user evidence before claiming 1.0 readiness.

The runtime currently declares ABI 1.3, executable envelope format 3, and
schedule-profile schema `tensor.schedule-profile.v1`. Package version `1.0.0`
does not require renumbering any of those contracts merely to match it.

## Milestone sequence

| Milestone | Outcome | Exit gate |
|---|---|---|
| M1 — Define the contracts | Public API, distribution identity, support tiers, and compatibility policy are explicit | Reviewed contract inventory and decision record; every advertised feature has a stability label |
| M2 — Make releases compatible | Released wheels, artifacts, modules, and caches survive supported upgrades | Frozen fixtures pass upgrade/negative tests; fingerprint-bound workload upgrades are explicit |
| M3 — Make discovery a product surface | Kernel authors can use a reusable, bounded, correctness-gated trial workflow | CUDA and WebGPU examples run through the same documented API; profiles replay and invalid trials cannot win |
| M4 — Establish release evidence | Current candidate files pass packaging, runtime, provider, and tutorial acceptance | Required jobs pass on the supported matrix, with hardware evidence tied to the exact candidate |
| M5 — Beta and release candidates | External users complete the intended workflows and release operations are rehearsed | Feedback triaged, blocking defects resolved, clean release rehearsal, and an unchanged final candidate accepted |
| 1.0 — Publish the contract | Reviewed files, release notes, and maintained compatibility guarantees | All required gates satisfied; publication is a separate explicit release action |

M2 and M3 follow the contract decisions in M1. Their implementation can proceed
independently. M4 validates their combined result; M5 exercises the product and
the release process together. Use interim `0.x` releases for feedback and
`1.0.0rcN` for candidates after the contract is frozen. No version bump is
performed by adopting this plan.

## M1: Define and freeze the public boundary

**V1-01 — Public API inventory.** List supported imports, signatures, defaults,
exceptions, buffer ownership, stream ordering, synchronization, and thread-safety
rules. Include the top-level workbench, modules, manual backward, and selected
discovery APIs. Document what remains an implementation detail, particularly
provider/compiler helpers currently used by benchmark scripts.

**V1-02 — Distribution and version policy.** Decide whether to retain
`tensor-workspace` as the public distribution name or migrate it before 1.0.
Check registry ownership and provide a migration path if renamed. Establish one
package-version source and checks against CLI metadata. Define compatible core
dependencies for optional packages and clearly label packages that remain `0.x`.
Keep exact tested pins until their replacement is implemented and validated.

**V1-03 — Compatibility policy.** Specify supported upgrades for Python APIs,
CLI/JSON, runtime ABI, `.tbin`, `.tpack`, manifests, locks, and profiles. Inventory
older formats still accepted by the code and deliberately retain or retire them
before the freeze. Define deprecation warnings and migration notes; avoid silent
semantic changes in 1.x minor or patch releases.

Recommended policy: compatible core 1.x updates retain the frozen 1.0 runtime
and module contracts. Existing executable images do not require rebuilding just
because Python source files moved. New artifact capabilities can require a newer
runtime and must be rejected clearly by older runtimes. Compiler/frontend reuse
has its own exact-version rules. Any incompatible stable-contract change requires
a major release or an explicitly versioned opt-in format.

**Exit:** a contract/stability reference and an ADR record these decisions. The
installation, runtime, module, and discovery guides agree with that inventory.

## M2: Compatibility and release identity

**V1-04 — Frozen compatibility fixtures.** Retain small released wheels, artifacts,
module closures, locks, and profiles with source/toolchain provenance. Test them
with newer candidate consumers, including fresh environments outside the checkout
and empty caches. Test both success and rejection: unsupported ABI/capabilities,
wrong target, changed payloads, ambiguous exports, stale locks, and missing images.
Exercise native header layouts with the corresponding host fixtures.

**V1-05 — Separate semantic compatibility from source identity.** Existing
training/inference bundles can hash implementation modules. Define the upgrade
rule for those bundles: retain their experimental exact-wheel pairing, or migrate
a selected stable bundle to a versioned semantic contract with explicit migration
and validation. Keep source hashes for provenance/cache invalidation. Do not
silently bypass existing fingerprint checks to make an upgrade pass. Experimental
optional bundles may retain exact-wheel requirements without blocking core 1.0.

**V1-06 — Dependency and cache policy.** Test clean cache, cache hit, corruption,
interrupted writes, and concurrent producers. Document compiler upgrade/rebuild
rules and validate the declared NumPy/wgpu/Python dependency ranges. Broaden a
range only after the corresponding matrix passes; supporting Python 3.12 alone
is sufficient for an accurately scoped initial release.

**Exit:** upgrading the supported core workflows has a reproducible pass/fail
contract. Users can determine whether an artifact executes unchanged, needs a
producer rebuild, or must stay paired with an older optional workload wheel.

## M3: Stabilize schedule discovery

The [current discovery guide](../guides/schedule-search.md) is the starting point.
Today `ScheduleSearch` proposes configurations while each workload owns its loop.

**V1-07 — Public discovery API.** Decide the supported import path and freeze
space, seed, family, legality, coupled-move, exhaustion, score, and selector rules.
Validate configurations and distinguish attempted, illegal, rejected, and measured
trials. Document reproducibility boundaries: deterministic proposals do not make
GPU timings or selected winners deterministic. If imports change, provide the
documented migration/deprecation path before the stable release.

**V1-08 — Reusable bounded trial runner.** Extract the recurring harness into a
small producer API with caller-provided build, correctness, measurement, and
cleanup hooks. Support candidate/time budgets checked at documented boundaries,
clear cancellation/failure behavior, versioned trial reports, and explicit timing
metrics. Do not imply that a wall-time budget interrupts an in-progress GPU call
or compilation. Keep the raw `ScheduleSearch` API available for custom workloads.
Include [TUNE-05 progress/events](tuning-workbench.md): live terminal status and
retained post-run trial history with budget denominators, current stages and best
valid results. Rich visual search/agent trajectories reuse the same event records.

**V1-09 — Validated profiles and replay.** Store semantic selectors separately
from schedule knobs, with source/toolchain/device provenance and a canonical
profile hash. Validate incorrect/nonfinite results before ranking. Rebuild and
recheck winners in a fresh process. Include the known-good baseline and replay
finalists under the same metric; record selected settings with the produced
bundle. Profile selection must have an explicit no-match/fallback rule.

Define the recipe/source closure and strict-identity versus requalification rules
in [TUNE-02](tuning-workbench.md). A winner can be reconstructed without retaining
its compiled artifact, but only with its definition and producer dependencies.
Profile hashes identify settings; executable identity, correctness and performance
replay remain separate checks. TUNE-01 supplies shared text/machine profiling
reports for humans and agents; optional visual and refinement interfaces reuse them.

**Exit:** a user adapts one existing TileLang factory, runs a bounded search,
inspects failed trials, selects a matching profile, and produces a compiler-free
artifact without copying a model-specific benchmark harness. CPU tests cover
search/report semantics; physical CUDA and WebGPU runs cover actual trials.
Cross-device performance portability and guaranteed optimization are not promised.

Generic search CLI syntax, distributed search, search resumption, and automatic
graph rewriting can follow 1.0. A minimal reliable Python workflow is the gate.

## M4: Supported environments and repeatable evidence

Use a small support matrix and qualify it with current candidate files. Proposed
initial tiers based on existing evidence are:

| Environment | Initial release intent | Evidence still required for the candidate |
|---|---|---|
| Linux x86-64 / Python 3.12 CUDA producer and consumer | Supported, with an exact-SM tested GPU profile | Clean producer-to-consumer transfer, runtime/interop, modules, and discovery on physical NVIDIA hardware |
| Windows x86-64 / Python 3.12 CUDA producer | Supported producer | Locked setup, NVRTC compilation, wheel/source builds, transfer to a matching supported consumer |
| Windows x86-64 / Python 3.12 WebGPU consumer | Supported bounded Vulkan profile on the tested AMD adapter | Physical RX 6700 XT correctness, features/limits, lifetimes, transfer, and discovery |
| Linux WebGPU | Software CI reference; promote physical configurations after candidate validation | Software correctness plus separate physical-adapter evidence for any supported GPU claim |
| Windows CUDA consumer | Preview until native Windows/NVIDIA execution is qualified | Actual Windows driver/runtime/interop acceptance; a Windows-produced wheel run on Linux is insufficient |
| macOS WebGPU | Preview until physical Metal acceptance | Candidate installation and bounded profile correctness on Apple hardware |
| Linux x86-64 CPU provider | Contract-validation reference | Shared runtime and native host checks; no optimized CPU performance commitment |

These are proposed tiers, not a change to current support claims. Maintain the
release matrix in [compatibility](../guides/compatibility.md) after qualification.
The requested [benchmark program](v1-benchmarks.md) adds A10G, L4, L40S, H100,
and B200 as explicit kernel evaluation targets, and L40S/H100 for Qwen inference.
This extends the earlier experimental benchmarking scope. Qualify those workloads
on actual hardware before claiming results; their evaluation list does not by
itself turn every architecture/platform into a stable provider support tier.

**V1-10 — Required release checks.** Combine distribution checks, ordinary tests,
frozen compatibility fixtures, and provider-specific acceptance into a release
checklist tied to an exact commit, wheel hashes, lock/toolchain versions, and
hardware/driver identity. GPU-free jobs can skip hardware tests; the corresponding
required hardware runs must execute their declared acceptance cases without
unexplained skips. Historical test totals are not a substitute for this evidence.

**V1-11 — Public-path tutorials and diagnostics.** Automate installation, existing
TileLang export/build/run, module packaging/transfer, and discovery/profile replay
using installed packages. Test errors for missing compiler/driver, incompatible
target, invalid arguments, rejected artifact, failed candidate, and missing profile
selector. Each diagnostic should identify the failing stage and an actionable
next step. Exercise the tutorials with fresh users in M5.

**V1-12 — Measured regression baselines.** Keep a small kernel/runtime set and a
representative optional workload as regression sentinels. Define timing protocols
and noise-aware regression thresholds before evaluating candidates. Investigate
regressions against the same hardware/precision/reference, rather than turning
llama.cpp, Triton, or PyTorch speed parity into a universal 1.0 gate.

Execute the broader [BENCH-01–09 comparison and demonstration program](v1-benchmarks.md)
as separately tracked release evidence. It requires new model/kernel implementations
as well as measurement infrastructure; existing bounded experiments do not satisfy
it. Retain unsupported reference cells and coverage gaps in the final report.

**Exit:** the advertised matrix can be reproduced for the release files, including
compiler-free consumers, explicit numerical checks, and documented skip reasons.

## M5: Beta, release candidates, and maintenance

**V1-13 — External onboarding.** Have at least two people outside the implementation
work reproduce the tutorials. Cover an existing-kernel author and a compiler-free
consumer; include discovery/profile reuse and module transfer between them.
Record confusing setup steps and fix issues without requiring private instructions.

**V1-14 — Release rehearsal.** Confirm distribution ownership and rehearse the
chosen publication channel using candidate artifacts. Prepare release notes,
migration instructions, support tiers, license/dependency notices, and artifact
retention. Verify downloads/installations of the exact files from that channel.
Use unique versions; treat uploading/publication as explicit release actions.

**V1-15 — Candidate acceptance and maintenance.** Define blocking severity and
triage ownership. A supported-path correctness, resource-lifetime, corruption,
upgrade, installation, or contract defect blocks release until resolved or the
advertised scope is explicitly revised. Run regression and compatibility checks
after a repair. Record who can publish patches, how releases are archived, and how
reported regressions receive a tested fix.

**Exit:** no unresolved release blockers, onboarding feedback is triaged, the
publication rehearsal passes, and the final unchanged candidate has complete
acceptance evidence. The release decision references that candidate, not an
earlier successful experiment or a partially tested rebuild.

## Priorities and tracking

All `V1-*` items above are planned; none is marked complete by this document.
Track implementation, verification, and accepted evidence separately.

| Priority | Items | Dependency |
|---|---|---|
| First | V1-01 public contract, V1-02 distribution/version policy, V1-03 compatibility | Establish M1 before making stable promises |
| Next | V1-04 fixtures, V1-05 bundle identity, V1-07 discovery contract | Follow the relevant M1 decisions |
| Then | V1-06 dependencies/caches, V1-08 runner, V1-09 replay, V1-11 tutorial checks | Build on compatibility/discovery contracts |
| Release validation | V1-10 required evidence, V1-12 baselines, V1-13 external onboarding | Qualify the integrated candidate |
| Final | V1-14 rehearsal, V1-15 candidate acceptance | Publish only after the required gates pass |

Each tracked item should link its implementation change, validation command or
runbook, candidate/version, and retained evidence. Mark it accepted only when its
exit criterion passes. Create repository issues from these items when scheduling
implementation; this plan does not create issues or assign dates/owners.

## After 1.0

Prioritize from real user needs while preserving the stable contracts:

- Additional Python versions, CUDA architectures, physical WebGPU adapters, and
  qualified Windows CUDA / Apple Metal consumers.
- Richer schedule spaces, resumable/distributed discovery, reusable profile
  registries, and user-facing search CLI ergonomics.
- More compiler lowerings, asynchronous execution improvements, and a native
  provider lifecycle interface.
- Wider inference/training coverage, explicit composition/fusion, and a possible
  standalone autograd layer as independently scoped projects.
- Direct PTX and alternate compiler experiments, retaining the existing post-v1
  decision until their compatibility and correctness are established.
- Proposed extras/addons for CPU/GPU workflow composition and SSD offloading,
  with explicit transfer, residency, prefetch and spill contracts. These remain
  after 1.0 and are outside the primary resident-GPU benchmark comparisons.

Keep these extensions outside the release gate unless a concrete 1.0 workflow
requires them. The first stable release should establish a maintained foundation
that later features can extend without restarting the user's integration.
